# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Use available skills (via the Skill tool) when they are relevant — for example, `/code-review` when reviewing changes, `/verify` when confirming a fix works, `/run` when launching the app, and `/security-review` for security-sensitive changes.

## Commands

```sh
cargo build                   # debug build
cargo build --release         # release build
cargo run -- <subcommand>     # run with args, e.g. `cargo run -- list`
cargo test                    # run tests
cargo clippy                  # lint
```

The binary is `target/debug/ichigo` (or `target/release/ichigo`).

Releases are built with [cargo-dist](https://github.com/axodotdev/cargo-dist) via `dist-workspace.toml` and the GitHub Actions workflow at `.github/workflows/release.yml`.

## Architecture

The project is a single-binary Rust CLI. Five top-level source files plus the `src/tui/` module:

**`src/main.rs`** — CLI entry point. Defines the `Cli` / `Commands` enum (via clap derive), dispatches to command functions (`cmd_new`, `cmd_run`, etc.), and embeds shell completion scripts as `const` strings. Chain detection is done by a simple `content.contains("steps:")` string check — there is no separate file format; a config is a chain if and only if it has a `steps:` key.

**`src/config.rs`** — All config types and file I/O. Two top-level config shapes: `RequestConfig` (single request) and `ChainConfig` (contains `Vec<RequestConfig>` as steps). Also defines `Body`, `Profile`, and `RequestEntry`. Key path logic:
- Local: `.ichigo/<name>.yaml`
- Global: `~/.config/ichigo/<name>.yaml`
- `resolve_config_path` checks local first, then global — local always wins.
- Names support `/`-delimited subfolders (e.g. `folder/request`), stored as subdirectories inside `.ichigo/`.

The same module's **user config** section is a different thing from a request config: `~/.config/ichigo/config.toml`, read once at launch by `UserConfig::load`. It is **TOML while requests are YAML, and that is load-bearing** — the two share a directory, and the differing extension is the only thing keeping them apart. `collect_yaml_entries` filters on `.yaml`, so it skips `config.toml` without being told to, and a request legitimately named `config` writes `config.yaml` beside it rather than over it. Teaching the request loader to read `.toml` would break both at once, which is why `USER_CONFIG_FILE` says so. An earlier `settings.yaml` needed a skip in the loader *and* a reserved-name refusal in `save_new_request` to get the same safety; the extension replaced both. File-shape and validated-shape are separate on purpose: `UserConfigFile` / `KeysFile` / `LayoutFile` are the file as written (every field optional so adding one never invalidates an existing file, `deny_unknown_fields` so a misspelled key is refused rather than ignored forever), and `UserConfig` is the validated form the TUI holds. `UserConfig` keeps `Keys` as its own type rather than flattening it: `Keys` is `Copy` and handed to the form handlers while they hold a `&mut` borrow of `App::mode` — copying it out first is what makes that split borrow legal — whereas the rest of the file is read once at startup and never needed in that position. A section per concern, so `split_pct` is `[layout]` and not a width inside a struct called `Keys`. Note `UserConfig::defaults()` rather than `Default`: derived, `split_pct` would be 0, a value `from_file` rejects. A bad value is **refused, not clamped**, and by name — the same bet as `deny_unknown_fields`, that a config which silently means something other than what it says costs more than an error does. There is no project-local override: these are per-user, not per-project.

**YAML parsing goes through `serde_yaml_ng`**, a maintained fork of `serde_yaml`, which was archived upstream and last published as `0.9.34+deprecated`. It is API-compatible, so the swap was the dependency and the module paths and nothing else. Do not "simplify" back to `serde_yaml`.

**`src/utils.rs`** — `send_request()` builds a blocking `reqwest` client and fires the HTTP request. `interpolate()` does `{{VAR}}` substitution: it checks the provided `vars` map first, then falls back to environment variables, leaving unresolved placeholders as-is (`{{VAR}}`).

**`src/curl.rs`** — Converts between a `RequestConfig` and a cURL command in both directions. Pure string work, no IO, unit tested.

`to_curl()` renders a config + resolved vars as a paste-ready command. It takes the same two inputs as `send_request` and **must stay in step with it** — a command that disagrees with what ichigo sends is worse than none. Substitution is shared via `utils::interpolate`; the duplicated rules (and the real drift risk) are query folding into the URL and the body's `Content-Type` header. Values are single-quoted unconditionally, with `'` escaped as `'\''`.

`from_curl()` is its inverse: it tokenizes with shell quoting rules (`'…'`, `"…"`, `$'…'`, `\`-continuations) and maps flags onto config fields. Two rules make the pair agree, and both are normalizations rather than transcription: a `Content-Type` header on a command with a body is stored as `body.content_type` and *never* in `headers` (`to_curl` re-derives it, so a config holding both emits the header twice), and a query string is lifted off the URL into `query` unless a key repeats or the URL carries `{{VAR}}`. The flag table is **deny-by-default** — an unrecognized flag is an error naming it, because a parser that skips what it does not understand turns `curl -F file=@x URL` into a bodyless GET and the user finds out against a real server. The round-trip tests at the bottom of the file are what keep the two directions honest; that is why both live in one module.

**`src/media.rs`** — Decides whether a response body is an image, and decodes it if so. Pure functions over a header string and a byte slice, no IO, unit tested — the same shape as `curl.rs`. Named `media` and not `image` because a top-level `mod image` is ambiguous with the `image` crate at every `use image::…` in the tree. `is_renderable_image` excludes **`image/svg+xml`**: it is markup the decoder cannot read, and its source is more useful in the text pane than a failed decode. `decode` guesses the format from the bytes rather than trusting the header — the header is what a server claims, the magic is what it sent — and runs under an encoded-size cap plus `image::Limits`, since a small file claiming enormous dimensions allocates before a pixel is read.

**`src/runner.rs`** — Executes a single `RequestConfig` (or one step of a chain). Handles profile variable injection, prints the response (status + body), and extracts values from the JSON response using dot-notation paths (e.g. `$.token` → `token`). Returns extracted variables so the caller can pass them to the next chain step.

**`src/tester.rs`** — Runs a request N times sequentially (blocking), collects per-iteration timings and status code counts, then renders an ASCII bar chart (status distribution) and ASCII line graph (latency over time).

**`src/tui/`** — The ratatui TUI, split across five files:
- `mod.rs` — `App` state, the `Mode` enum, the action paths (`try_run_selected`, `execute_request`, …), and the event loop.
- `tree.rs` — reading configs off disk (`load_entry` / `load_entries`) and the folder-tree model.
- `handlers.rs` — one key handler per mode.
- `render.rs` — all drawing.
- `edit.rs` — the caret and vim motions inside a single form field.

`App` holds the list of entries and a `Mode` enum that drives all rendering and input. Modes are:
- `Browse` → main list + detail pane
- `ProfileSelect` → pick a profile before running
- `VarInput` → fill in `{{VAR}}` placeholders before running
- `TestInput` → fill vars + iteration count before a load test
- `Response` / `TestResponse` → show results; `f` filters lines, `V`/`y` copy a line range. An `image/*` body renders inline under its summary line — see **Image responses**
- `NewRequest` / `NewProfile` → create/edit requests and their profiles in-TUI
- `ProfileList` → the draft's profiles; pick one to edit, add, or delete
- `EditPairs` → the draft's headers *or* query params as name/value pairs, per its `PairKind`
- `EditBody` → the draft's body: its content type and its data — see **The body pane**
- `ImportCurl` → paste buffer for importing a cURL command
- `ConfirmDelete` → confirm before deleting

**Text fields.** `edit::apply` is the only place a form field's characters are typed, deleted, or moved through, and `edit::Edit` (a byte caret plus an `insert` flag) is the only record of where the caret is. Fields stay plain `String`s: each *mode* carries one `Edit` beside its focus index, because only the focused field can be reached by a keystroke. That is also the invariant most easily broken — **every** place that changes `focused` must re-anchor the caret (`RequestDraft::focus`, `caret_for`, `Edit::at_end`), or Tab carries an offset from a long field into a shorter one. `apply` clamps the caret against the value on the way in rather than trusting it, so the cases nothing re-anchors — a draft that toured `EditPairs` and came back, a header row deleted at the focused index — cost a cosmetic keystroke instead of panicking on the next slice. `Mode::var_input` / `test_input` / `edit_pairs` / `new_profile` exist for the same reason: a form can open on a value prefilled from a profile, the environment, or disk, and building the variant by hand left the caret at 0 wherever the anchoring was forgotten.

Fields open in **insert** mode; `Esc` drops to **normal** mode, and only a second `Esc` leaves the pane. That is what makes `h`/`l`/`w`/`b` possible at all — in insert mode those are letters someone is typing into a URL — and it is why `Esc` is no longer a match arm in the form handlers: it reaches `edit::apply`, which reports `Applied::Exit` only from normal mode. Arrows and Home/End work in both modes, and Backspace deletes in both (vim moves left there; backspace-deletes is the one habit every text field shares, and normal mode already has `x`). There is deliberately **no hint** for any of this: the mode shows in the caret's shape, a thin bar for insert and a block over the character for normal, exactly as a terminal cursor would. `draw_response`'s own `j`/`k`/`V`/`y` bindings are a separate thing — a response pane is not a text field — as are the two incremental filters, where every keystroke re-filters and a motion key would have nothing to move.

**The row walk.** In normal mode `j` and `k` move focus *between* rows rather than a caret inside one. `edit::apply` reports them as `Applied::FocusNext` / `FocusPrev` and the pane performs the move, because which rows exist — and that four of the request form's are action rows with no text at all — is the form's business and not the caret's. Every pane with more than one field honours them (`NewRequest`, `EditPairs`, `EditBody`, `NewProfile`, `VarInput`, `TestInput`), and all of them, together with Tab and BackTab, walk through `step_row`, so no two of them can end up wrapping differently. `EditBody`'s data row is the one place `j`/`k` are not *only* a row walk: they move by line while there is a line to move to, and report the walk only off the top and bottom — see **The body pane**. A focus move also **carries the mode** — that is what the flag on `Edit::landing` is for — and Tab carries it too rather than as a second rule: a walk is not a decision about typing, and landing in insert would make the second `j` of a two-row hop a literal `j` typed into the field it just reached. Fields still *open* in insert mode; that is the `Mode` constructors' `Edit::at_end`, as is the `Edit::default()` a `Ctrl+a` row starts from. On an action row `j`/`k` walk in **either** mode, since there is nothing to type there and `j` onto `global` would otherwise be a one-way trip out of the walk — and `walk_key` repeats the `Ctrl+<letter>` refusal `edit::apply` makes centrally, so an unbound `Ctrl+j` cannot move the focus instead. The response pane and the two incremental filters are untouched: `draw_response`'s own `j`/`k` already scroll it, and a filter has no rows to walk.

`edit::apply` also owns the refusal of `Ctrl+<letter>`, which is what keeps a handler's `_` arm from typing the letter of an unbound chord.

**Two-key commands.** The `d`/`c`/`y` operators, `f`/`F`/`t`/`T`, `r` and `gg` all read a second key, and all of them are one `Edit::pending_cmd` armed by the first and consumed by the second. `apply` **takes** it on the way in, exactly as it takes the insert-escape `pending`, which is what makes every key that does not reach the normal-mode table cancel it — a `d` left armed across an arrow key would delete a word the next time someone typed `w`. `complete` is where the second key lands, and a key that cannot finish the command is *discarded* rather than re-read as a fresh one, so a mistyped `dq` is inert instead of arming a delete for the next keystroke. `apply_multiline` owns Enter and `j`/`k`, so those clear it themselves (in `vertical` and the two Enter arms); the two states can never be armed at once, since one only arms in insert mode and the other only in normal.

Plain motions and operator motions read **one** table, `simple_motion`, so `w` and `dw` cannot drift apart about where a word ends; it returns the target plus whether an operator over it covers the character it lands on, and `op_span` turns the pair into a byte range. Two things there are load-bearing. `word_forward` returns `value.len()` rather than the last character when there is no next word — `rest_on_char` pulls a plain `w` back onto the character, so the motion is unchanged, but vim's `dw` on a line's last word takes the rest of that line and stopping a character short would leave one behind. And `h`/`l` are clamped to the line, which they were not before: in the body they could step onto a `\n`, which is not a position normal mode has.

**The register.** `p` puts what `y`, `d`, `x`, `s`, `D`, `C` or `S` last took, and it is one `String` on **`App`**, not on the focused field's `Edit` — the point of a register is to carry text *between* fields, and scoping it the way the undo history is scoped would make `y` and `p` useless together. It reaches `edit::apply` as a `&mut String` argument; each handler takes it out of `app.register` alongside the `let keys = app.keys` copy, a second disjoint field borrow beside `&mut app.mode`. `cut` is the single path every removal goes through, which is what keeps the register filled without seven sites remembering to. It is **charwise and only charwise**, `dd` and `yy` included: every field but the body is a single line that must never gain a newline, and a linewise register would put one there the first time someone yanked a body line into a URL. The cost — `yy` then `p` inserts at the caret rather than opening a line below — is documented in the README rather than fixed. `dd` and `S` likewise take the line's *text* and leave its newline, so deleting a line does not join the line below onto the one above.

**Undo.** `u` in normal mode pops `Edit::history`, a stack of `Snapshot { value, caret }`. The unit is a *change*, not a keystroke: `Edit::record` is called at each mutation site, and in insert mode it records only once per session (`session_saved`), so everything typed between `i` and `Esc` collapses into one `u`. `s`/`C`/`S` and the `c` operator both edit and open a session, so they record their edit and then set `session_saved` to fold the typing that follows into it. Every `record` sits *inside* the guard that checks the mutation will actually happen — a Backspace at position 0 or an `x` past the end must not push an entry that restores identical text, which would read as a broken `u`. This is also why the history is **not** seeded at construction: `Edit::at_end`'s argument would have to be the field's true current value at every call site, and `Edit::default()` (used for a freshly added header or param row) has none to give — a wrong seed would make `u` blank the field rather than merely misbehave. Recording at the point of mutation is the only place the current text is known for certain.

Two consequences worth keeping: `Edit` is **no longer `Copy`**, because the history is a `Vec` — the renderer takes `&Edit` (it only ever reads `caret` and `insert`), and every other holder already worked through `&mut`. And the history dies with the `Edit`, so undo is per-field and a focus change clears it; `MAX_UNDO` only bounds a long session inside one field. There is no redo stack.

**The insert-escape sequence.** `keys.insert_escape` in `config.toml` is vim's `inoremap jk <Esc>`: a two-key sequence that leaves insert mode. Exactly two, because the pending first key is a single `char` in `Edit` — a longer sequence would need a `String` there and `Edit` would stop being `Copy`, which is what lets it live inside a `Mode` and be handed around by value. The first key is inserted into the field like any other character and *un-typed* when the second completes the sequence; `completes_escape` re-checks the character before the caret against the pending one rather than trusting the flag, so a mismatch degrades into a plain insert instead of deleting whatever is there. `apply` does `edit.pending.take()` unconditionally on the way in, which is what makes every other key disarm the sequence — miss that and a `j`, three cursor moves, and a `k` would escape. `insert_str` clears it too. The one-second `SEQUENCE_TIMEOUT` is vim's `timeoutlen` and is checked against an `Instant` when the second key arrives, so it needs no tick in the event loop; it rescues a pause between the keys, not a fast literal `jk`.

**Headers and query params.** Both are edited in **one pane**, `Mode::EditPairs`, which carries a `PairKind` naming which of the draft's two maps it is showing. They are the same screen — two fields per row, the same Tab walk, the same `Ctrl+a` / `Ctrl+d`, the same edits-live-in-the-draft-until-saved contract — so a second mode, handler, and renderer would have been three places for a caret fix to be made twice and applied once. Everything that genuinely differs hangs off `PairKind`: the title and noun (so the pane never says "header" while editing query params), and `apply`.

Enter on the form's `headers` or `query params` row opens the matching pane; `Ctrl+e` (with `Ctrl+h` as an alias) and `Ctrl+q` are accelerators for the same thing. `Ctrl+h` must never be the *only* binding for headers — many terminals and tmux configs bind Ctrl+H to backward-delete-char and send `0x7F`, which arrives as a plain Backspace and silently deletes a character. `Ctrl+q` is safe for the analogous reason it looks unsafe: raw mode clears IXON, so it is no longer XON/XOFF flow control. Either way the Tab row is the path nothing can intercept, which is why both panes are reachable without knowing a chord at all.

`apply_headers` and `apply_query` are where the rules diverge, and the divergence is the point. Both drop blank-named rows and trim names and values. Headers refuse duplicates **case-insensitively**, because HTTP does not distinguish case and a `HashMap` would silently keep whichever row landed last; query params refuse them **case-sensitively**, because a query key is opaque to the server and `page` and `Page` are two different params — refusing that pair would reject a request that is perfectly legal to send. A duplicate still has to be refused for query, since `query` is a `HashMap` and one of the two would otherwise vanish; it is the same constraint that makes `from_curl` decline to lift a repeated key out of a URL. The `Content-Type` normalization is **headers-only**: a query param that happens to be named `Content-Type` is just a param, and must not touch the body.

Note that `Ctrl+<letter>` reaches a handler as `KeyCode::Char` **plus** a CONTROL modifier, so text-entry arms must exclude it — before `Ctrl+h` existed, pressing it typed a literal `h` into the focused field. Form fields are safe because `edit::apply` refuses modified keys centrally, and `handle_key` now refuses them for Browse too — Browse reads only the `KeyCode` and binds bare letters, so `Ctrl+q` used to run the `q` binding and quit the TUI. That was survivable while nothing taught anyone to press it; it stopped being so once `Ctrl+q` meant "query params" one pane away, since a chord worth learning must not end the session where it is not bound. Browse has no chords of its own, so the refusal costs nothing. The two filter handlers still match bare `Char(c)` and still have that bug.

**The body pane.** `Mode::EditBody` is the draft's `body` — its `content_type` on row 0, its `data` on row 1 — reached by Enter on the form's `body` row or by `Ctrl+b`. It is a separate mode from `EditPairs` rather than a third `PairKind` because a body is not a list of pairs: two fixed rows, no `Ctrl+a`/`Ctrl+d`, and one of the two rows holds newlines. That last part is what everything else here follows from.

`Ctrl+s` applies and **Enter types a newline**, which is `ImportCurl`'s contract and not `EditPairs`'s, for `ImportCurl`'s reason: a terminal without bracketed paste delivers a pasted JSON body as characters with Enters between the lines, so an Enter that applied would keep the first line and throw the rest at the pane's own bindings. On the content-type row, where a newline means nothing, Enter steps down to the body — the one key must not mean "save" on one row and "newline" on the next.

`edit::apply_multiline` is the door for the data row, and it is a wrapper around `apply` rather than a flag inside it: only Enter and `j`/`k` differ, and everything else — insert, motions, undo, the insert-escape sequence — has to stay the *same* code, or the body field drifts away from the fields around it. `j`/`k` move by line while there is a line to move to and report `FocusNext`/`FocusPrev` only off the top and bottom, so the row walk still works at the edges while `j` in a twenty-line body does the useful thing. The motions that are *about* a line — `0`, `^`, `$`, `A`, `I`, `D`, `C`, `S` — are measured against the caret's line rather than the whole value, which matters most for `D`: whole-value truncation would have made `D` on line one delete the body. On a value with no newline in it a line *is* the whole value, so every other field is unchanged, and that is the property to preserve when touching `line_start` / `line_end`. `rest_on_char` also refuses to leave a normal-mode caret on a `\n`, since that is not a character you can sit on.

`apply_body` owns the three-way decision about whether the request still has a body. **Blank data removes it**, content type and all — an empty body is not a body, and this is the only way to take one off a request. **Data with a blank content type is refused by name**, not defaulted: the field opens filled in, so a blank one is someone having cleared it. **Any body takes the `Content-Type` header over**, which is `apply_headers`'s and `from_curl`'s normalization run in the create direction — a bodyless request may legitimately carry that header, and adding a body is the moment it stops being where the value lives; holding both puts it on the wire twice, since `to_curl` re-derives it. `Mode::edit_body` seeds the field from that header when there is no body, from the body when there is, and from `DEFAULT_CONTENT_TYPE` otherwise — a visible default in an editable field, the same thing `RequestDraft::blank` does with `GET`. That constant is deliberately *not* `from_curl`'s `application/x-www-form-urlencoded`: that one transcribes a command someone else wrote, this one starts a body nobody has sent yet.

Unlike every pair pane, the data is **not trimmed** — leading whitespace and a trailing newline are bytes the server may be counting. The content type is, because it is a header value.

Two rendering consequences. `text_area_lines` splits the data on `\n` and gives the caret to the one line whose byte range holds it (a caret at a line's end belongs to that line; the next starts past the newline), which is why `field_spans` was split into `spans_with_caret` — the caret has to be re-measured from its own line's start. And `body_preview` caps what the *form* shows at `BODY_PREVIEW_LINES` with a count of the rest: the form is one `Paragraph` with no scrolling, so an eighty-line body would push `profiles` off the bottom, and a Tab stop focus can land on invisibly is the thing the action rows were introduced to stop.

`Ctrl+b` is tmux's prefix key, so under tmux it never arrives. That is a reason to be sure the `body` row exists, not a reason to pick a worse letter — an accelerator tmux swallows costs a tmux user nothing, whereas `Ctrl+h` had to gain an alias because it *arrives as a different key*. The `NewRequest` hint line does not advertise it: at 85 columns it would breach the 80-column rule that governs that line.

**Keeping the caret on screen.** The form panes are `Paragraph`s with no wrapping, so a value wider than the pane was simply cut off at the border — and with it the caret, which made walking through a long bearer token a matter of guessing where the cursor had got to. `render::window` slides a character window along the value instead, and `input_line` draws `‹`/`›` where text is hidden. It is recomputed each frame from the caret rather than stored and nudged: there is then no scroll offset to keep in step with a value the form can replace underneath it (a draft that toured `EditPairs`, a row deleted at the focused index — the same class of staleness `edit::apply`'s caret clamp exists for). The price of being stateless is that the window centres on the caret rather than following it lazily, so text slides under a caret crossing the middle of a long value; that is vim's own `scrolloff=999` and is the better half of the trade against losing the caret off the edge. Both markers are paid for whenever windowing happens at all, even when only one is drawn — charging for them as they appear would shift the text by a column for a reason unrelated to the caret moving. Only the **focused** row is windowed: without a caret there is no one place that has to be visible, and a window would just hide the start of the value. `window` is a function of three counts so it can be unit-tested, the same reason `split_pct_at` and `image_area` are.

**And vertically.** The same panes were `Paragraph`s with no *scrolling*, so a form taller than the pane was cut off at the bottom border — and the request form is taller than most panes the moment a request has headers, so Tab walked focus onto rows that were not drawn at all. `render::vscroll` is the vertical half of `window` and is stateless for the same reason: a form's lines change under it (a header row deleted at the focused index, a draft that toured another pane), so an offset stored and nudged would be describing a list that no longer exists. Each renderer records the lines its focused row occupies in a `FocusRows` as it builds them — a pane knows which row is focused only as it draws it — and hands that to `vscroll` at the end. It **centres** the focused row, exactly as `window` centres the caret and at the same price, and the centring is load-bearing twice over: it is also the slack that lets the two *wrapping* panes scroll on an estimate. Two guards on the arithmetic: never past the end of the content (a pane showing blank rows below the last line has scrolled past it), and never past the focused block's own first line, so a block taller than the pane shows its top rather than centring a middle that would take the top off the screen.

`EditBody` and `ImportCurl` wrap, and a wrapped `Paragraph` scrolls by **rendered rows, not lines** — so for those two, `wrapped_offsets` re-counts every line through `wrap_starts`, an estimate of what `Wrap { trim: false }` does (break at the last space that fits, mid-word for a word wider than the pane). Only the widget knows for certain where it broke a line; a row of disagreement costs a row of centring rather than the caret, which is the whole reason `vscroll` centres rather than pinning to an edge. `body_caret_row` then finds the caret's row *inside* its own line, because a body that is one long line of JSON is the common case and its line's first row is as far off the bottom as no scrolling at all. `ImportCurl` needs no caret at all: the buffer is only ever appended to, so the row to keep on screen is the last one there is.

The Browse **detail** pane is deliberately not part of this: it has no caret and no focused row, so scrolling it means new keys in a mode whose `j`/`k` already drive the list.

**Response lines.** `visible_response_lines` is the single definition of which lines the filter leaves showing, and `draw_response`, `G`, cursor movement, and both copy paths all read it. It exists because those had already drifted: the predicate was spelled out separately at each site and the copy path never got one, so filtering to two lines and pressing `c` handed over the whole body. `cursor` and `anchor` index *that* list, not `body.lines()`, which is why every edit to the filter resets them — carrying them over leaves the cursor on an unrelated line and a selection spanning lines the user never saw. The pane scrolls to follow the cursor rather than the reverse, so a selection cannot be extended past the edge of the view. `Esc` drops a selection before it leaves the pane, and the selection highlight is a base `Line::style` so `colorize_json_line`'s colours survive it.

**Image responses.** An `image/*` body is read with `bytes()` and drawn in the response pane through `ratatui-image`; everything else still goes through `text()`. The branch has to be taken *before* the body is consumed, since `text()` and `bytes()` each take the response by value — reading an image as text is the lossy-UTF-8-over-binary mojibake this exists to stop. `Mode::Response` carries the decoded image beside `body`, so it dies with the pane the way every other mode's state does; that is also what makes `Mode` un-`Clone`able, since `StatefulProtocol` is not. `body` is **always** the summary line (`image/png · 100×100 · 7.9 KB`) whether or not the image renders, which is what lets the filter, `V`/`y`, and `visible_response_lines` keep working on real text with no image-shaped exception. Every failure below the request — unreadable body, failed decode, no protocol — degrades to summary-plus-note rather than to an error pane: a `200` we could not decode is still a `200`, and showing it as an error would misreport the server.

Chain steps get the summary line and no image. The chain pane is one combined text block, and the step's `text` is left **empty** so a step that also declares `extract` fails with the honest "response is not JSON" rather than on mojibake.

**Protocol detection** is `ratatui-image`'s two-stage probe, the same shape yazi's `yazi-adapter` uses: guess from `$TERM`/`$TERM_PROGRAM`, and where that says nothing, write control sequences and read the reply. It runs once, from `App::new`, which is why `run` builds the `App` *before* `enable_raw_mode` — the reply arrives on stdin and the alternate screen must not be up yet. `Halfblocks` is refused deliberately: it would render something in any terminal, but a quarter-scale mosaic of colour blocks in the response pane reads as what the server sent, and it isn't. The `is_terminal` guard on both stdin and stdout is **load-bearing and not an optimization** — `ratatui-image` runs the query on a detached thread and abandons it after one second, but the thread has no timeout of its own and blocks in `stdin().read()` until something parses as a Device Status Report. Where nothing ever answers, it goes on eating the keys meant for the event loop and then calls `disable_raw_mode` under a TUI already running in it. `ichigo | cat` (the query goes down the pipe) and `ichigo < /dev/null` (`read` returns `Ok(0)` forever and its loop spins) are the two ways to get there, and the guard is what refuses both.

Halfblocks is also what `from_query_stdio` reports when the terminal answered the graphics query but *not* the cell-size one, and that is a different thing entirely — which is what `recover_protocol` is for. The crate falls back to its default picker whenever the cell size is unknown, and that fallback **discards the capabilities it just collected**, so a terminal that replied `OK` to the kitty query and ignored `CSI 16 t` is indistinguishable from one that replied to nothing. Multiplexers land there: herdr forwards the kitty protocol to its panes but answers neither `CSI 14/16/18 t` nor `TIOCGWINSZ` with pixel dimensions, so ichigo told anyone running it under herdr that their terminal had no image protocol while it was drawing images for everything else. The recovery is to ask again and read the reply for the protocol alone, and it runs **only** down that path — a terminal that works today never reaches it, so the second query cannot cost a working setup anything. `ASSUMED_CELL_SIZE` is then the cell size, and is a deliberate *under*-estimate: the kitty images `ratatui-image` emits are virtual placements with no `c=`/`r=`, so the terminal derives their footprint from transmitted pixels ÷ its own real cell, and guessing high crops the image to its top-left corner while guessing low merely draws it smaller than the pane. A cell is reported in device pixels, so the same font is ~8×16 on one display and ~17×39 on a HiDPI one — the spread is too wide to split, and small-and-complete is the readable half of it.

**tmux** draws no images of its own. It has *passthrough* — a `\x1bPtmux;…\x1b\\` wrapper it forwards to the terminal it is attached to — and both the capability query and every transmitted image ride through it, so both are dropped unless the pane's `allow-passthrough` is on. `prepare_tmux` sets it with `tmux set -p`, which is a **pane** option: nothing in the user's `tmux.conf`, and gone with the pane. `ratatui-image` writes the wrapper, but only where it believes it is under tmux, which it decides from `TERM` starting with `tmux` or `TERM_PROGRAM` being exactly `tmux` — neither true for `default-terminal "screen-256color"` before tmux 3.5, the release that started setting `TERM_PROGRAM`. `$TMUX` is set by every tmux for every pane, so that is what ichigo tests, and where the two disagree it sets `TERM_PROGRAM` to the string the crate is looking for. That is the one `env::set_var`, and why detection is the first thing `App::new` does: the process is still single-threaded there, before the crate's query has spawned its reader.

The flag then has to be threaded all the way into `recover_protocol` — an *unwrapped* second query under a multiplexer is not a second opinion on the terminal but a first opinion on tmux, which answers `CSI 5 n` and `CSI c` itself and forwards neither. That is how a kitty-capable setup ends up drawing sixels (tmux's own DA1 advertises them where it was built with sixel support), or nothing at all.

`TMUX_PIXEL_BUDGET` is the third thing tmux costs, and the one that made a real response show nothing at all. tmux collects a passthrough sequence into one bounded buffer — `INPUT_BUF_LIMIT`, 1 MiB — and past it **discards the sequence whole** rather than truncating it: no bytes reach the terminal, no error is reported, and the pane fills with placeholder cells addressing an image that was never transmitted. Measured against tmux 3.5a, 1,048,000 bytes of payload go through and 1,048,570 do not, and the same total split across 256 KiB sequences goes through completely. `ratatui-image` wraps the *entire* chunked kitty transmit in one sequence (its own comment says otherwise; the code does not), so the only lever here is how many pixels go into it — a 2121×1414 JPEG in a HiDPI pane came to 2.9 MB and vanished. What the budget bounds is the image **as transmitted**, not the one handed to the widget: the resize target is rounded up to whole cells, so a transmit runs up to a cell wider and taller than its source, and budgeting the source is what let the same photograph through at 522×380 — 13 KiB over the limit and dropped exactly like the uncapped one. `budget_dimensions` therefore solves the quadratic for the padded size, and `Resize::Fit` never scales up (`min(area, source)`), so nothing grows past it afterwards. The cap binds only under tmux and only past roughly 500×350; the real fix belongs upstream, in chunking the passthrough per kitty chunk.

`TMUX_DEFAULT_CELL_SIZE` is the other half, and is the reason images under tmux were **cropped rather than missing**. Inside tmux `TIOCGWINSZ` always has an answer: tmux sets its panes' pixel dimensions from the attached client's, and where the client reported none it fills in `DEFAULT_XPIXEL`/`DEFAULT_YPIXEL` — 16×32 — instead of leaving them zero. `ratatui-image` prefers a `CSI 16 t` answer (which survives the passthrough, and is the terminal's own measurement) and falls back to `TIOCGWINSZ`, with no way to tell a fabrication from a measurement — so a 64×64 image was scaled against 16×32, placed on a 4×2 grid of placeholders, and the terminal, dividing by its real ~9×20 cell, drew the top-left quarter of it. Under tmux exactly that size is therefore read as "no answer" and replaced with `ASSUMED_CELL_SIZE`. The recovery path above is *not* the one that catches this: with the kernel always answering, tmux never reaches it.

`image_area` is the arithmetic for the rows the image gets — below the body text, one blank row between — and is its own function so it can be unit-tested, the same reason `split_pct_at` is one. It returns `None` rather than a zero-sized `Rect` when the pane is too short or has been dragged to no interior at all.

**Profiles.** `ProfileList` is the only door into `NewProfile` — Enter on the form's `profiles` row and `Ctrl+p` both land there, so add/edit/delete all start from one screen. Its rows are `0..profiles.len()` plus a trailing "new" row, which is why an empty list opens with "new" already selected. `NewProfile` carries `editing: Option<usize>`, and `upsert_profile` uses it to replace rather than push; without it, editing a profile and keeping its name appended a second profile under that name and the picker could only ever reach the first. That index also makes a name clash decidable — a profile keeping its own name is not a clash, a profile taking a sibling's is, and the second is refused because a duplicate is unreachable from both the picker and `--profile`. Edits mutate only the draft; `save_new_request` remains the single path that writes a config, so Esc out of the form discards profile changes too.

Inside `NewProfile`, a profile's params are added with `Ctrl+a` and removed with `Ctrl+d` — the same two chords `EditPairs` uses, because it is the same shape of list and a param pane that added but never removed meant the only way out of a wrong key was to blank both its fields and rely on `save_new_profile` dropping blank-named rows. `Ctrl+d` is inert on focus 0: that row is the profile's name, not a param. It clamps `focused` to `2 * params.len()` and re-anchors the caret through `profile_field`, which for a deleted last param lands on the name — the same obligation every focus change carries, and the reason the arm cannot just `remove` and return.

**The help overlay.** `App::show_help` is a `bool`, not a `Mode` variant, because the `?` keymap draws *over* the current pane and dismisses back to it — as a mode it would have to record which of the eleven it interrupted. `draw` renders it last so it lands on top of both panes and the hint line, and `handle_key` checks it first, swallowing the dismissing key: letting it through would make `d` close the overlay *and* open the delete confirmation behind it. `?` only opens from Browse, since every other mode is either a text field where `?` is a literal character or a pane whose own hints already fit. The Browse hint line is deliberately short (7 entries, 61 columns) — it once listed all fifteen bindings at 155 columns, which an 80-column terminal truncated silently, hiding the last five. It carries the actions someone reaches for without looking (`r t n e f ? q`); everything else belongs in `HELP_COLUMNS`, and anything added here has to be measured against 80 columns first.

**Unsaved changes.** `save_new_request` is the only thing that writes a config, and every sub-pane applies into the draft rather than to the file — so a form can hold a header, a body and three profiles that exist nowhere else, and Esc used to drop all of it silently. `RequestDraft::baseline` is a `DraftSnapshot` of what a save would have written when the draft was last in step with disk, and `is_dirty` compares the current one against it. The snapshot is the **saved shape**, not the draft: no caret, no focused row, and the four text fields normalized through `normalized_fields`, which `save_new_request` also uses — one definition, so the marker cannot disagree with the save about whether a trailing space in a URL is a change. A form that called itself unsaved for having been tabbed through would teach people to ignore the marker, which is the only thing it has to offer. The baseline is *what is on disk under this draft's identity*: `from_config` with an `original_name` starts clean, and without one (a clone, an imported cURL command) starts from a blank form's snapshot, so everything it arrived with is unsaved — which it is.

`App::confirm_discard` is then the prompt, a `bool` for the same reason `show_help` is one: it draws over the form and answers back to it, and as a `Mode` it would have to carry the draft across and hand it back untouched — a second owner of the thing it is protecting. `handle_key` checks it before every mode and `handle_paste` refuses while it is up, or the key answering it would also be typed into the field underneath. Unlike help, a key that answers nothing leaves it standing: `s` saves and closes, `y` discards, `n`/Esc keep editing, and everything else is swallowed, because a prompt guarding work about to be lost must not be dismissible by whichever key was hit next. The one door it guards is Esc out of `NewRequest` (`App::leave_form`) — Esc in the sub-panes returns to the form, which still holds every edit and now says so.

Variable placeholder names are extracted by `extract_var_names` (scans url, headers, query, body for `{{...}}`) to build the `VarInput` field list. The TUI clipboard copy (`c` key) uses `pbcopy` and is macOS-only.

**`RequestDraft`.** `NewRequest` and `NewProfile` both hold a `RequestDraft` — the four editable fields plus the headers, query, body, and extract the form edits in its sub-panes or (in `extract`'s case) does not edit at all. Those are carried in the draft rather than re-read from disk at save time, because an imported or cloned request has no file to re-read; recovering them from disk silently dropped them (which is why `c` used to clone only a request's method and URL). Build a draft through `RequestDraft::blank()` or `from_config()`; `edit_selected` / `clone_selected` / `confirm_import_curl` are the three entry points.

**Form focus.** `draft.focused` walks `rows()` stops, not `fields.len()`: the four text fields, then five *action* rows — global, headers, query, body, profiles — so everything a request has is reachable by tabbing rather than by knowing a chord. Headers, query, and body sit in that order because that is the order a request config lists them in. Read it through `focus_target() -> Focus`, never by comparing against `fields.len()` at the use site; `Focus::Field(i)` is the only variant that may be handed to `edit::apply`, and passing an action row would index `fields` out of range. Enter therefore means two things — save from a field, do the row's thing on an action row — and the `_` arm means two things as well: on an action row there is no insert mode to leave, so one `Esc` exits where a field takes two, and every other key is inert rather than typed. `focus()` re-anchors the caret only when it lands on a field; an action row leaves the stale caret alone, which is safe because no field's index can match `focused` there. The action rows are also why `profiles` renders when empty — it did not before, and a Tab stop that disappears is one focus lands on invisibly. Browse deliberately has **no** `h`, `q`, `b`, or `p`: headers, query params, the body, and profiles are parts of a request, not actions on one, and routing them through the form means they cannot be edited without the request in front of you.

**Pasting.** The event loop enables bracketed paste (`EnableBracketedPaste` on entry, `DisableBracketedPaste` on exit — skip the latter and the terminal keeps emitting paste markers) and handles `Event::Paste`. `handle_paste` has to serve every text field, not just the import buffer — miss one and pasting into it is a silent no-op, which is exactly what `EditPairs` did until it got an arm. It lands text at the caret via `edit::insert_str`, so a paste behaves like typing rather than always appending. Enter in that pane inserts a newline and `Ctrl+s` confirms, precisely because a terminal *without* bracketed paste delivers a multi-line paste as characters with Enters between the lines; binding Enter to confirm would parse only the first line.

**The draggable split.** The divider between the list and the detail pane is dragged with the mouse, which is the whole of what the mouse does — `handle_mouse` grabs on `Down(Left)` within `DIVIDER_GRAB` columns of the divider, tracks `Drag(Left)`, and lets go on `Up`. It is deliberately **mode-independent**: both panes are drawn in every mode, so widening the detail pane to read a response works the same as widening it to fill in a form, and a drag never competes with a keystroke a text field would rather have as a character. `split_pct` is seeded from `layout.split_pct` and moved by dragging, and a drag is **not** written back to the file — the config is the width a session starts at, and a drag to read one long response should not silently become the permanent setting. It is a percentage, not a column count, so the ratio survives a terminal resize *and* a config file means the same thing on two different terminals. `MIN_SPLIT_PCT` / `MAX_SPLIT_PCT` live in `config.rs` with one definition serving both the drag clamp and the file validation — the same bounds for the same reason, and putting them there keeps the dependency pointing the way it already does (tui → config). `split_pct_at` is its own function so the arithmetic is unit-tested, and it is the **inverse of the layout solver** — the divider is drawn at the right pane's first column, so the left pane is exactly `column` columns wide — rounded to nearest, because truncating makes the divider trail the pointer by a column on the first drag event. `render::draw` records `split_x` and `term_width` each frame rather than letting the handler re-derive them: a click has to be tested against the frame the user is looking at, and re-solving the percentage repeats the solver's rounding and lands a column off on some widths. `term_width` is 0 before the first frame, which is why `split_pct_at` returns an `Option` instead of dividing by it.

This costs the terminal's own click-drag text selection while ichigo is up — `EnableMouseCapture` routes those events to the app — which most terminals give back under Shift (Option on macOS); the response pane's `V`/`y` copy never depended on it. `DisableMouseCapture` carries the same must-be-on-every-exit-path obligation as `DisableBracketedPaste`.

**Pending actions.** `ProfileSelect` and `VarInput` are shared by every action that needs a profile or variables, so each carries a `PendingAction` (`Run` / `Test` / `Curl`) naming its destination. Both `confirm_profile_select` and `handle_key_var_input`'s Enter dispatch on it. A new action must set it at *every* construction site of both modes — miss the `VarInput` one and the action silently falls through to running the request, because that is where the pipeline used to be hardcoded. `Mode::Response` likewise carries a `ResponseKind` (`Http(u16)` / `Error` / `Curl`) instead of encoding "not a response" as status `0`; build it through `App::show_message` / `show_error` rather than spelling out the variant.

**Config freshness.** The TUI is meant to stay open for long sessions, so no action may rely on the entry snapshot taken at startup. `App::entries` is a display cache only. Every action path (`try_run_selected`, `try_test_selected`, `confirm_profile_select`, `start_chain`) re-reads the config through `tree::load_entry` before deriving profiles or `{{VAR}}` names — those feed the vars map, and `interpolate` prefers that map over everything else, so a stale value there silently wins over a correct one in the file. On a load failure the action aborts via `App::show_error`; it must never fall back to the cached entry. `R` in Browse mode calls `reload_entries` for a full resync (picks up files added/renamed/deleted on disk); `r` is run. Environment-sourced `{{VAR}}` values cannot be refreshed — the process env is fixed at launch.
